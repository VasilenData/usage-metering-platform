FROM SOURCE TO A LOCAL EXPORT

Three steps. Real API requests.

Install Git, Python 3.12+ and Docker with Compose v2 first. Start Docker. Commands run from your own local checkout.

01

Get the full source

The ZIP includes the example client and guide. Clone the repository for the Compose stack and restricted API.

git clone https://github.com/VasilenData/usage-metering-platform.git
cd usage-metering-platform
02

Check, configure, start

Diagnose dependencies, create separate private local passwords, and start PostgreSQL plus the API. Repeated setup preserves your saved credentials and data.

python3 -m starter.local doctor
python3 -m starter.local setup
python3 -m starter.local up

The API stays on 127.0.0.1:8000. PostgreSQL stays inside Docker's private network. First build downloads images and packages.

03

Send, replay, correct, reconcile

Use the real HTTP API to produce both statements. The client checks the event count, units, amount and unchanged original revision before writing your export.

python3 -m starter.client
EXPECTED SUCCESSPASS: 12,000 - 2,000 = 10,000 units;
USD 3.00 -> 2.50; delta -0.50.

Your private export: .meterwork/first-use/result.json

RERUN WITHOUT GUESSING

Your next run is defined.

The client saves identity before retrying. No auto-reset, credential rotation or silent replacement of a failed result.

Repeat the example

Run the client again within one hour. It reuses the sandbox and event IDs; result bytes and statement IDs remain unchanged.

After expiry, choose a fresh name with --workspace next-demo. Previous local exports remain.

Pause and keep your data

python3 -m starter.local stop
python3 -m starter.local start
python3 -m starter.local backup

Stop/start keeps the named database volume. Backups stay private and get unique filenames.

When something fails

Missing Docker? The diagnostic tells you what to install or start. Port busy? Free port 8000. HTTP 429? Wait one minute.

An unknown response may follow a commit. Rerun the same workspace. Interrupted sandbox creation stops for an explicit decision.

Upgrades, backups and an intentional reset

Back up before upgrading; retain the source commit and credentials privately. Verify restoration in a separate database before relying on the backup. Major PostgreSQL upgrades need a tested migration. Normal commands never remove the volume.

Follow the upgrade and recovery guide ↗. The separate destructive reset instructions clearly identify the data they remove.
