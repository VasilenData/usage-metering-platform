# Restoring the current restricted application runtime

A restored ledger is not sufficient evidence that its application can restart safely. `pg_restore --no-owner` assigns restored functions to the restoring identity, and omitted ACLs do not recreate the reviewed execution boundary. Meterwork now has a separate executable recovery gate for the **current HTTP runtime**, rather than treating the older offline Store restoration as equivalent.

**Scope:** generated accounts and usage, two fresh databases on one dedicated PostgreSQL cluster, and real loopback Uvicorn processes. No hosted backend, public traffic, customer data or cloud resource is involved. The cluster roles already exist from source bootstrap; this is **not a blank-cluster role migration or a production recovery runbook**. The archive is generated by this exercise from its own trusted source database. Never restore an untrusted dump with this administrative procedure.

## Recovery boundary

1. Create a fresh source fixture with the real restricted API. Account A publishes an original statement and a correction; B publishes a separate statement. Expire a third account and stop the source API.
2. Capture a custom-format backup. Create an independent destination from `template0`, revoke PUBLIC `CONNECT`, and restore with `--no-owner --no-acl --exit-on-error --single-transaction`. Runtime admission remains closed.
3. Prove the negative case: the runtime cannot connect, and all five restored control functions are owned by the restoring administrator rather than the reviewed `meter_control` owner.
4. Call the new **access-only** `configure_runtime` path. It reinstates the fixed functions' owner, search path, explicit execution grants and token-derived policies. It does not run `Store` initialization, seed fixtures or alter financial history. Hash every column of all five data tables before and after this step; require exact equality, including account metadata and token digests. Values remain private; evidence includes only row counts and fingerprints.
5. Inspect function ownership and PUBLIC ACLs administratively, grant destination `CONNECT` to the restricted login, and require the existing `RuntimeStore` startup checks to pass. Start a new actual API process with only its runtime DSN; no administrative/test DSN or bootstrap password is inherited by that child.
6. Verify original statement IDs, contents and cutoffs, token-derived account separation, expired-token denial, idempotent replay, rejected foreign correction and a new valid revision. Reconcile each A revision using independent SQL at its original knowledge cutoff. Restart the API once more and require unchanged history.

The new entry point is [verify_runtime_restore.py](../verify_runtime_restore.py). [configure_runtime](../bootstrap_runtime.py) separates access provisioning from the unchanged initial demo bootstrap. The existing `RuntimeStore` verifies the role, effective grants, reviewed function ownership and enforced row policies before readiness.

## Acceptance criteria

| Boundary | Required observation |
|---|---|
| Complete data | All five tables' row counts and every-column fingerprints equal the source immediately after restore and after access configuration. |
| Initial admission | Restored destination denies runtime connection before permission hardening; source login/HTTP was demonstrably working. |
| Definer ownership | Five fixed functions have `meter_control` NOLOGIN nonsuperuser ownership, `search_path=pg_catalog`, and no PUBLIC execution. |
| Direct SQL | An A token with B's UUID and an unfiltered query reads only A. Foreign inserts, price updates, role creation, control-role assumption and token-hash reads return actual privilege errors. |
| HTTP | Original A/B histories remain separate; a forged query selector still reads A; the expired account receives 401; a foreign correction receives 422. |
| Financial continuity | A's original 100-unit/25,000-micro-USD statement and 80-unit/20,000 revision survive. Retrying old usage creates no new revision. A late 40 units produces revision 3 with 120 units/30,000 micro-USD; B remains 4,250 micro-USD. |
| Independent reconciliation | Separately written SQL matches every A revision's units and amounts at its immutable knowledge cutoff. |
| Second restart | Another fresh API process reads the same history using the restricted DSN. |
| Source isolation | Target-only replay and late usage leave all five source-table fingerprints unchanged. |

## Run the gate

Use a **dedicated disposable PostgreSQL cluster**, a control database ending in `_test`, matching-major-version `pg_dump`/`pg_restore`, and `requirements-dev.txt`. Supply `TEST_DATABASE_URL` privately in the environment, then:

```sh
python verify_runtime_restore.py --pg-bin /path/to/postgresql/bin --output local-evidence/runtime-restore.json
```

The script generates both database names; it never accepts a user-selected overwrite destination. A database is removed only after this invocation successfully creates it, including on assertion failure. The source API stops before backup and the destination API stops before cleanup. Temporary dumps contain hashed sandbox tokens and are deleted on exit; do not publish them. An existing output path is rejected to preserve previous evidence.

The exercise provisions a fresh random **cluster-global** runtime login password. Therefore it must not share a cluster with an active Meterwork application. The new password stays inside the test process and its restricted child environment. PostgreSQL commands receive connection credentials through environment variables, not command-line URLs or reports. A real incident procedure would need independently governed credential delivery and revocation decisions.

CI runs this gate after the HTTP and runtime-privilege exercises, then checks the report's recorded source hashes against that exact checkout. Successful runs retain `runtime-restore-ci.json` in the `postgres-test-evidence` artifact. The gate's checks and request statuses are distinct from the earlier 345/363-request exercises; those historical reports are not rewritten.

## What remains outside this proof

This demonstrates one controlled same-cluster database restoration and restart. It does not establish WAL/point-in-time recovery, a fresh-server role migration, network/TLS controls, power-loss durability, an internet-facing deployment or sustained service availability. A dump recovers the state at backup time; writes and credential revocations after that snapshot are not magically recovered. The elapsed exercise time includes backup, hardening and assertions and is not a recovery SLA. Implementation is AI-assisted; no external reviewer, real adoption or unaided owner performance is implied.

## Delivery prompt and primary references

The task prompt adapts the project's evidence-first delivery workflow:

> Preserve immutable statements and all restored records. Reproduce the exact ownership/admission gap, restore only into a newly created disposable database, and keep application access closed while administrative repair runs. Separate access configuration from seeding. Check complete data equality, effective PostgreSQL permissions and actual restarted HTTP behaviour; use independent fixture arithmetic and SQL, not only a green health endpoint. Record source/runtime identity and bounded results. Keep credentials and dumps private, preserve older reports, and state same-cluster/global-role and production limitations.

PostgreSQL documents that [users/roles must exist before restoring ownership and permissions](https://www.postgresql.org/docs/17/backup-dump.html), that [pg_restore ownership/ACL options and single-transaction execution change the restore boundary](https://www.postgresql.org/docs/17/app-pgrestore.html), and that [SECURITY DEFINER functions need controlled search paths and execution privileges](https://www.postgresql.org/docs/17/sql-createfunction.html). These references guide the implementation; they are not endorsements or external reviews.
